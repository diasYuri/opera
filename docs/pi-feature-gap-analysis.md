# Mapeamento de recursos: Pi e Opera

**Escopo:** comparação do produto `pi` (principalmente `packages/coding-agent` e as APIs `pi-ai`, `pi-agent-core` e `pi-tui` que ele integra) com o CLI Opera deste checkout. O Pi foi inspecionado em `~/git/other/pi-mono` em 2026-11-16. O inventário do Pi vem de código e documentação do repositório; o do Opera foi cruzado com implementação, documentação e matriz de cobertura do SDK.

Este documento lista recursos do Pi sem equivalente no Opera ou com cobertura apenas parcial. “Parcial” significa que existe uma capacidade próxima, mas não o mesmo fluxo, interface ou superfície de extensão. Bibliotecas do monorepo Pi que não são recursos do CLI (por exemplo, Chord e Durable) não são contadas como gaps do produto.

## Resumo

As diferenças mais importantes são:

1. **Ecossistema extensível do Pi:** extensões JS/TS executadas no processo, API rica de eventos e UI, gerenciador de pacotes e prompts/templates/temas distribuíveis. O Opera tem extensões WASM consentidas e algumas contribuições declarativas de UI, mas não oferece as mesmas APIs nem instalação de pacotes.
2. **Integrações de modelos:** o Pi tem um catálogo muito maior de provedores nativos, configuração profunda de endpoints/modelos, integração direta com llama.cpp e classes de modelos para classificação e geração de imagens. O Opera cobre os provedores OpenAI, Anthropic, Google, OpenAI-compatible e ChatGPT subscription via seu harness atual.
3. **Superfície interativa e de automação:** o Pi oferece RPC JSONL bidirecional de longa duração, SDK TypeScript embutível, comandos de shell no editor, editor externo, clipboard de imagens e export/share de sessão. O Opera oferece execução durável, JSONL de eventos, chat acessível, retomada e exportação JSON redigida, mas não esses mesmos fluxos.

## Gaps de fidelidade da TUI e da extensão

Além dos fluxos acima, a extensão Pi pode customizar o próprio editor (incluindo prompt e comportamento de input), adicionar widgets/status/footer, definir autocomplete providers e renderers de mensagem/ferramenta, abrir diálogos e registrar atalhos/flags. Opera permite algumas adições declarativas de UI, mas controla integralmente editor, layout e renderização. Assim, “suporta extensões” não significa paridade de extensibilidade.

O Pi também tem `/settings` configurável e `keybindings.json` para ações do app/editor. Opera permite alterar configurações previstas no schema e a aplicação tem keymap implementado, mas não oferece o mesmo arquivo/superfície de remapeamento de atalhos ao usuário.

## Recursos do Pi que **não** são gaps do Opera

Estes são exemplos importantes que a comparação não deve classificar como faltas:

- **Subagentes e execução de tarefas:** Pi declara que não inclui sub-agents nem plan mode por padrão. Opera oferece task manager, workers/subagents locais persistidos, limites compartilhados, cancelamento e approvals.
- **Aprovação e recuperação duráveis:** Pi não tem o fluxo Opera de política por operação, diff aprovado vinculado a precondição, checkpoint/SQLite, retomada de aprovação pendente e reconciliação de efeito incerto. Essa é uma vantagem de Opera.
- **Contabilidade auditável:** Opera mantém ledger durável de cada invocação, proveniência de custo/preço e separação entre conhecido/estimado/indisponível. O Pi mostra uso/custo na sessão e agrega chamadas de codemode, mas o mapeamento do Pi não mostra ledger de execução com as garantias e estados auditáveis do Opera.
- **Aprovação de extensões por conteúdo/concessões:** Opera exige consentimento explícito e vincula-o à configuração/bytes/grants para WASM e MCP. Pi usa confiança de projeto, mas declara que não tem sistema interno de permissão para restringir filesystem/processo/rede/credenciais.
- **LSP e ferramentas de código integradas ao produto:** Opera inclui busca AST, outline e navegação semântica LSP escopada quando compilada com o recurso correspondente. Pi entrega ferramentas básicas `read/grep/find/ls` e deixa maior parte das ferramentas especializadas para extensões/pacotes.

## Capacidades sem equivalência direta

Opera acrescenta algumas capacidades de produto que não são parte do coding-agent Pi padrão: memória local persistente com aprovação explícita para gravar/apagar; MCP/WASM encaminhados pelo runner durável; gestão de operações incertas; política `ask/read-only/trusted`; UI acessível append-only; e processo de execução foreground sem daemon. Não são gaps do Pi, embora algumas possam ser montadas por extensões no ecossistema Pi.
